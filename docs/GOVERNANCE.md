# Data governance notes

A small, local version of the governance a lakehouse needs: where each dataset comes from, under what terms, who
may see it, how it is checked, and how the layers depend on each other.

## Sources and licence

All input data comes from **LTA DataMall** (Land Transport Authority, Singapore). LTA's DataMall licence page
(checked 2026-09-27, [datamall.lta.gov.sg](https://datamall.lta.gov.sg/content/datamall/en/SingaporeOpenDataLicence.html))
states that DataMall data is made available under the **Singapore Open Data Licence version 1.0**, whose text is at
<https://data.gov.sg/open-data-licence>. The licence requires attribution in this form, with a link to the licence:

> Contains information from {name of dataset} accessed on {date of access} from LTA DataMall which is made
> available under the terms of the [Singapore Open Data Licence version 1.0](https://data.gov.sg/open-data-licence)

For this repository:

| Dataset (DataMall endpoint) | Accessed | Used for |
|---|---|---|
| Traffic Speed Bands v4 (`v4/TrafficSpeedBands`) | 2026-09-26 to 2026-09-27 (sampled snapshots) | speed-band bronze, link and congestion marts, ML features |
| Traffic Speed Bands v4, link geometry | 2026-09-26 | `dim_link` |
| Passenger Volume by Bus Stops (`PV/Bus`), Feb, Jun, Jul, Aug 2026 | 2026-09-26 | stop demand mart |
| Passenger Volume by Origin Destination Bus Stops (`PV/ODBus`), Jul, Aug 2026 | 2026-09-26 | top OD flows mart |
| Bus Stops, Bus Services, Bus Routes | 2026-09-26 | stop names, network dimensions |

Other terms of the licence that matter here: the data comes with no warranty, no official endorsement may be
implied, and it grants no rights over personal data. None of these datasets contains personal data: passenger
volumes are monthly aggregates per stop or stop pair.

This repository uses no URA data. (The companion repository `sg-bus-network-monitor` uses URA Master Plan 2019
layers, which are published on data.gov.sg under the Singapore Open Data Licence.)

## What is committed and what is not

- **Not committed:** raw DataMall files, bronze/silver/gold tables. They live in the local MinIO buckets or a
  local `.lake/` directory and are rebuilt by the pipeline.
- **Committed:** code, a small **synthetic** fixture (`tests/fixtures`, generated by `tests/make_fixture.py`,
  no real values), and aggregate results under `results/` (counts, hashes, quality findings, timings, and a
  report with charts and a top-10 OD table).
- **Keys:** the DataMall AccountKey is read from `LTA_KEY` at run time by the optional live mode and is never
  written to disk. MinIO credentials are local development values in `.env` (git-ignored; template in
  `.env.example`).

## Provenance

Every run records its inputs:

- `results/batch_ingest.json`: for each monthly or static file, its name, size, SHA-256, the row count and volume
  sums from an independent Python pass over the raw file, rows loaded, rows quarantined and why.
- The same SHA-256 and source row count are written into the metadata of the Delta commit that loaded the file
  (`DeltaTable.history()` shows them next to the version they produced).
- `results/speedband_files.json`: for each speed-band snapshot, its event time, SHA-256, source rows, rows
  quarantined, repeated links, and rows added to bronze.
- Bronze speed-band rows carry `_source` (stream or file), `_ingested_at` (UTC) and `_late` (the consumer's
  watermark verdict). Stream messages that could not be decoded are kept in `bronze/_dead_letter/speedband_stream`
  with their topic, partition, offset and the reason.

## Classification

| Layer | Content | Access in a real deployment |
|---|---|---|
| bronze | data as published, types enforced | data engineers |
| silver | typed, cleaned, conformed dimensions | analysts, data engineers |
| gold | marts and ML features | anyone with access to the open data |

All layers carry `contains_pii: false` in the dbt `meta` block. In a cloud lakehouse these would map to catalog
grants (for example Unity Catalog or Lake Formation); here there is only one local user, so the table is
documentation, not enforcement.

## Catalogue and lineage

- `docs/CATALOG.md` is generated from the dbt manifest by `tools/catalog.py`: every model and source with its
  description, columns, tests and upstream dependencies, plus a lineage graph.
- `make docs` also builds the interactive dbt docs site (`dbt docs generate --static`), which is not committed.

## Quality controls

1. **Ingest:** header must match exactly; malformed lines and values that fail a cast or a domain rule are
   quarantined with a reason (`bronze/_quarantine/<dataset>`); bronze + quarantine is reconciled with row counts
   and volume sums taken independently from the raw files (`results/profile_bronze.md`).
2. **dbt tests:** not-null, unique and composite keys, accepted values, ranges, relationships, and singular tests
   (bronze partition equals event time; an episode stays within one sampling run and covers consecutive
   snapshots; gold keeps every silver row through its inner joins; the calendar's years have public holidays).
3. **Custom checks** with documented thresholds (`config/quality_thresholds.yml`), reported in
   `results/quality_report.md`. Airflow runs them in strict mode without retries, so an error-severity failure
   stops publishing.
